# 网页版玩家数据迁移调研

## 实现结果

网页版与本地程序版均在设置页「存储」卡片下方提供「导出数据」和「导入数据」。每次导出所有已保存的本地账号。导入前可预览数量，确认后统一写入独立的新账号；目标端保留原先选中的账号。备份文件记录来源端的选中账号，同一文件重复导入会得到提示。

## 实现前的调查

7.2.05 的首页是 `src/pages/about/IntroPage/IntroPage.vue`，目前没有整库导出或导入入口。圣遗物页、角色预设页、UID 数据页和轴编辑器都有专项导出。单 UID 包按 UID 筛选，并会调整装备引用，不能靠拼接多个 UID 包还原整个仓库。

在线迁移已有另一条路径。在「设置 → 账户管理与同步」登录，按本地账号选择「关联当前账号并自动同步」，核对已启用的数据类别并点「立即同步」。目标端登录同一在线账号后可以「下载为新本地账号」。计算历史走单独的同步接口。只登录并不等于所有本地账号都已备份。[云档案界面](../../../src/pages/OnlineAccountPage/CloudProfilesPanel.vue) · [同步类别](../../../src/cloud/sync-categories.mjs)

## 文件应包含什么

| 范围 | 一次完整迁移需要保留的内容 |
| --- | --- |
| 本地账号 | 当前来源下所有仍列在账号列表中的档案、名称，以及当前选中哪个账号；同名账号也分别保留。 |
| 圣遗物与配装 | 五个部位的完整仓库，包括未装备、未归属 UID 的物品和面板相同的多件物品。保留原始物品 ID、角色预设、武器配置、配装收藏及文件夹，以维持装备引用。 |
| UID 与角色 | 各 UID 的角色快照、条目、选中 UID、与预设和装备的关联、导入与撤销记录、对比历史和对比设置。独立创建的角色预设也要导出。 |
| 四人轴 | 已保存的轴库、当前选中项、下一个编号、个人任务及其轴和 UID 对应关系。编辑器里还没保存的草稿要先保存。 |
| 计算历史 | 单人和四人计算的历史列表、状态以及每条记录的完整详情，包含当时的输入、配装和结果。库存后来变更，旧结果仍应能打开。 |
| 界面偏好 | 语言、外观可作为独立可选项，在目标端选择是否应用。云绑定、设备标识、统计同意状态及可重建缓存留在原设备。登录令牌、米游社 Cookie、服务地址、密钥和本机服务目录不进入备份文件。 |

账号档案的七组存储字段已有统一映射。历史的索引和详情另存；UID 专项包中的历史与计算历史也属不同内容。[档案映射](../../../src/cloud/profile-sync.ts) · [UID 导入记录](../../../src/import/import-history.mjs) · [计算历史](../../../src/algorithms/calculation-history.mjs) · [轴库与任务](../../../beta-data/team-dps-library.mjs)

## 建议的导出和导入接口

1. **主页「导出数据」** 调用前端备份函数，在玩家平时使用的浏览器和原网址读取档案；目标端无需访问旧站或登录。浏览器存储按来源隔离，用域名保存的数据与同机回环地址下的数据应分别导出。[IndexedDB 来源隔离](https://developer.mozilla.org/en-US/docs/Web/API/IndexedDB_API/Basic_Terminology#key_characteristics)
2. **备份文件** 使用带格式标识、格式版本、应用版本、导出时间、备份 ID、当前账号引用和账号列表的 JSON。提取现有档案字段表供云同步和文件迁移共用。用允许列表读取玩家数据，保持原始关联和历史详情。等账号初始化及存储、轴任务、历史的待写入操作完成，再取得一致快照；遇到进行中的计算或缺失的历史详情应指出具体档案和记录。页面可复用现有文件下载函数。[文件下载](../../../src/utils/common.js) · [写入队列](../../../src/store/backend.ts)
3. **本地程序主页「导入数据」** 选择文件后只读预览账号名、UID 数、圣遗物数、轴数和历史数。确认后为来源账号分配新的本地账号 ID，并保留各账号内部物品 ID、轴编号及其引用。按版本校验结构，区分原本已卸下或删除的装备与文件中意外缺失的数据。遇到不支持的版本应说明原因。为同一备份记录导入标识，重复选择文件时可识别已恢复的账号。
4. **恢复提交** 把账号列表、七组档案、各账号的历史索引和详情、导入标识准备好后，用一次 IndexedDB 写事务提交，再刷新账号和历史视图。可以抽取现有历史导入的编号映射逻辑；直接依次调用云档案恢复和历史导入会产生两次独立提交。旧目录同步的 `LocalBackend.importContent()` 会先清库再逐项写入，不适合作为玩家备份恢复入口。若启用目录镜像，要单独报告镜像写入失败，避免把已写入数据库的存档重复导入。[存储实现](../../../src/store/backend.ts) · [事务语义](https://www.w3.org/TR/IndexedDB-3/#transaction-construct)

## 实现验收

用合成档案从网页导出，在带有已有账号的本地程序导入并重启。核对多账号、多 UID、未归属物品、同面板重复物品、角色装备与配装收藏、四人轴个人任务和历史详情。对重复导入、未知版本、历史正文缺失及存储空间不足分别验收。另测含大量计算历史的备份体积和读写峰值，再决定是否需要压缩或分段读取。

整库迁移回归见 `tests/account-backup.test.mjs`，涵盖历史详情、四人轴任务、UID、角色和仓库的往返、同名账号、重复文件、残留账号编号和异常文件。生产构建已在两份独立浏览器存储之间用合成档案验证导出、预览、取消、导入、重新打开和重复导入。
