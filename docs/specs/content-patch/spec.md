# 内容补丁（热更新）

Status: ready-for-human

2026-11-20 与开发者对齐方向，搭档提出需求。动手前先读根目录 `AGENTS.md`，它的规则优先于本规格。任务在 `issues/`，按依赖顺序做。待决定的事已在 2026-11-20 按推荐定下，见「待开发者决定」。

## 给执行者

- 一个任务一次本地提交，不推送、不建 PR、不发布、不部署服务器。
- 补丁不能改变没有被补丁覆盖的任何计算结果。
- 校验和签名是新增校验，开发者批准本规格即视为同意加在补丁入口；入口之外不重复校验。
- 每轮验证不超过五项。汇报时写清实际跑了什么，没在真实安装包或手机上点过就不说实测通过。

## Problem Statement

现在改一个数据错误（比如某把武器的数值填错）只能发新版本：搭档的更新流程是检查 GitHub 或 CNB 的 Release，下载完整安装器或 zip 再覆盖安装。这有三个问题：

- 项目规则要求发布必须开发者明确授权，账号还曾因一小时内连发多个版本被暂停，不能把每个小修都发成 Release。
- 玩家要下载整个安装包，只为一两个数值。
- 官方体验服版本的数值经常需要回头修正，等下一个正式版本太慢。

## Solution

在 Release 之外加一个**内容补丁通道**。补丁是一个很小的、带签名的数据包，只替换已登记的数据文件（JSON 和数据模块），不含任何可执行代码。

- 补丁清单放在一个固定的静态地址，写补丁号、适用的基础版本、每个文件的 sha256 和下载地址。
- 客户端启动时查一次清单，之后每隔几小时查一次。有更新就下载，校验签名和哈希，通过后放进用户数据目录的**覆盖层**，下次启动生效。
- 读数据时先读覆盖层，没有再读安装包里的原文件。删掉覆盖层就是回滚。
- 补丁号接在基础版本后面，例如 `7.2.05EA.01`。界面、Debug 导出和使用统计都显示它。
- 界面代码、规则代码和 `mona_wasm_bg.wasm` 内核**不能**热更，这些继续走 Release。

### 能热更的范围

只有「纯数据」可以进补丁。已知的数据来源：

| 位置 | 内容 | 现在怎么进程序 |
| --- | --- | --- |
| `beta-data/weapons-release-71.json`、`weapons-signature-release-71.json` | 武器数值 | 编译进前端包，经 `composeKernelApi({data})` 传入 |
| `beta-data/vodyanitsa.json`、`extension-support.json` | 角色数据、扩展支持表 | 同上 |
| `src/assets/_gen_character.js` | 角色数据 | 同上 |
| `beta-data/weapons-expanded-runtime.mjs`、`silver-light-runtime.mjs` | 扩展武器数据 | 作为模块被 `expanded-weapons.mjs` 静态导入，不经 `data` 参数 |
| `beta-data/team-dps-native/*.json` | 四人轴计算图 | 被 Worker 静态导入 |

**三个入口都要接**：浏览器入口 `mona_wasm/pkg/index.js`、四人轴 Worker 的 `src/wasm/team-dps-native-api.mjs`，以及测试用的 Node 入口 `beta-tools/runtime.mjs`。它们现在各自重复写了数据加载，补丁要让三处读到同一份数据，否则测试覆盖不到页面实际运行的计算。

`equipment-effect-values.mjs`、各类规则书这类 `.mjs` 是代码，**不进补丁范围**。把它们改成数据文件是另一件事，不在本规格内。

## User Stories

1. 作为开发者，我想发一个很小的补丁来修正一把武器的数值，而不用发完整版本。
2. 作为开发者，我想补丁发出后玩家在几小时内就能拿到，不用等下一个正式版。
3. 作为开发者，我想补丁只能替换登记过的数据文件，以便不会误改规则代码和内核。
4. 作为开发者，我想补丁带签名，以便被劫持的下载地址不能给所有玩家推改过的数值。
5. 作为开发者，我想一条命令就能打出补丁包并签名，以便发补丁不会出错。
6. 作为开发者，我想补丁标明适用的基础版本，以便新版本发布后旧补丁不会覆盖新数据。
7. 作为开发者，我希望补丁下载失败时玩家无感，继续用已有数据，下次再试。
8. 作为开发者，我希望能一键回滚补丁，以便补丁本身有问题时恢复原始数据。
9. 作为开发者，我希望 Debug 导出里写明当前补丁号和各文件哈希，以便玩家反馈计算问题时知道算的是哪份数据。
10. 作为开发者，我希望使用统计能区分补丁号，以便看到补丁的覆盖进度。
11. 作为开发者，我希望三个入口读到的是同一份数据，以便测试覆盖页面实际的计算。
12. 作为玩家，我希望补丁在下次启动时才生效，以便计算到一半时数据不会变。
13. 作为玩家，我想在设置里看到当前补丁号，也能关闭自动补丁。
14. 作为玩家，我希望离线时软件照常可用。

## 补丁包格式（草案）

```
manifest.json    补丁号、基础版本范围、文件清单（路径、sha256、大小）、创建时间
<数据文件…>      每个文件对应一个登记过的数据位置
manifest.sig     对 manifest.json 的 Ed25519 签名
```

- 清单里的补丁号全局递增；同一基础版本下，新补丁是**完整的覆盖集**，不是在上一个补丁上叠加，这样客户端只要拿最新一份。
- 基础版本范围用现有版本比较规则判断；超出范围的补丁客户端直接忽略。
- 文件只能写在登记表允许的路径上，不允许 `..` 或未登记的路径。

## 开发环境的登录逻辑热更新

开发服务沿用设置页的「自动获取内容补丁」。每次检查时，原有地址提供计算数据，下面的 `auth/` 子目录提供登录程序。两边分别编号、验签和保存。开发服务从启动配置读取地址、公钥和基础版本。Windows 成品和 Android 当前未启用登录通道。

- `server/auth-rules/qr-exchange.json` 的 `request` 构造国服 V2 请求体，`response` 将上游的 `data` 映射为本机读取的票据和账号字段。换票地址、目标票据类型、扫码身份校验和绑定 UID 查询由本机服务负责。
- `server/auth-rules/cloud-import.json` 的 `fields` 在云端保险箱解密后选择 Cookie 字段，可以按字段是否存在走不同分支。输入是已有字段名，输出指定同类字段的来源或用 `null` 忽略该项。解密、校验绑定角色和保存凭据由原有代码执行。
- 程序以 JSON 表示。普通对象构造结果，`{"$read":"a.b"}` 读取标量，缺失时返回 `null`。`{"$eq":[a,b]}` 做严格比较，`{"$if":[条件,成立时的表达式,否则的表达式]}` 选择分支。每个文件最多 16 KiB，每个入口最多 256 个节点、16 层。程序只处理本次调用的输入。

本机生成测试包时，用现有 `patch-tool.mjs build` 命令，将上述两个相对路径作为末尾参数，输出到本机测试补丁站点的 `auth/`。基础版本范围应覆盖开发客户端的 `displayVersion`，`MONA_PATCH_SIGNING_KEY` 指向与测试公钥配套的私钥。单独跑下面的集成测试会自动生成临时密钥并在回环地址提供测试包。

```powershell
node --test tests/auth-content-patch.test.mjs
```

每个登录包是一份完整快照。修改一个入口时，把另一个仍需保留的程序一并打包。下载、验签、校验文件和编译表达式全部成功后，新扫码和下一次云端导入立即使用新快照。已生成的二维码走原来的规则。回退时用更高补丁号打包旧规则，将入口文件内容改为 `null` 可恢复内置规则。重新启动会对本机存档重新验签。调试信息的 `auth` 字段记录当前补丁号和最近一次检查结果。
