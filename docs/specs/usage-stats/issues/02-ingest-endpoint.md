# 02: 在线服务接收上报

**What to build:** 在线服务能接收客户端发来的使用统计：校验通过的记录按"匿名安装 ID + 功能 ID + 日期 + 平台 + 版本"去重入库，并同步更新累计汇总；不合格的请求被拒绝并返回原因；同一个 IP 发得太频繁会被限流。

**Blocked by:** 01

**Status:** done

规格见 `docs/specs/usage-stats/spec.md` 的「在线服务」。2026-11-12 开发者已确认下面的校验规则。

- [x] 在线服务里新增一个独立的使用统计模块，不读写账号、会话、Cookie 托管和快照相关的表
- [x] 新增迁移文件，接在现有迁移之后：一张明细表（上面五个字段唯一），一张累计汇总表（按功能、平台、版本记录用过的安装数）
- [x] 上报接口：一次请求带一个匿名安装 ID、平台、版本和一组"功能 ID + 日期"
- [x] 校验：功能 ID 必须在登记模块里；安装 ID 必须是 UUID；平台必须是已知值（Windows、Android）；日期和服务器当天最多相差 2 天；单次条数有上限
- [x] 只要有一条不合格，整个请求拒绝，响应里写明是哪一条、什么原因
- [x] 重复上报同一行直接忽略，累计汇总不重复计数
- [x] 按连接来源 IP 限流，IP 只在内存里用，不写库、不写日志；沿用现有的可信代理配置
- [x] 登记模块随在线服务的部署包一起打包，不复制第二份；打包脚本相应调整
- [x] 测试用现有的 PGlite 夹具，通过 HTTP 覆盖：每类校验拒绝、去重、累计汇总不重复计数、限流
- [x] 验证：只跑在线服务的新测试文件

## Comments

- 2026-11-12：上报接口是 `POST /v1/usage-stats`，不需要登录，放在登录校验之前。请求体 `{installId, platform, version, records: [{feature, day}]}`，成功返回 `{accepted: 条数}`。
- 累计表和规格原文不同：存的是"安装 ID + 功能 ID + 平台 + 版本"一行（附首次日期），不存计数。原因是同一个安装在两个版本都用过某功能时，按版本存计数再相加会算成两个人；存行之后按任意筛选 `count(DISTINCT install_id)` 都准确。这张表不随 400 天清理删除。
- 新增了版本格式校验（以字母或数字开头，只含字母、数字和 `.+-`，最长 32 位），防止任意字符串写进库。平台取值 `windows`、`android` 放在功能登记模块里，客户端和服务端共用。
- 限流：每个 IP 每 10 分钟 120 次，只存在进程内存里，窗口切换时整体清空；`rate_limits` 表不写入。单次最多 500 条、请求体最多 64 KB。
- 验证：`online-service/tests/usage-stats.test.mjs` 4 项通过；原有 `backend.test.mjs`、`profiles.test.mjs` 4 项通过；`tests/usage-stats-features.test.mjs` 4 项通过。打包脚本没有实际运行。
- 2026-11-12（后续）：开发者决定把离线补发放宽到 30 天。日期规则拆成两个上限：过去最多 30 天，未来仍然最多 2 天，都写在登记模块的 `USAGE_UPLOAD_RULES` 里。
- 2026-11-12：开发者确认保留版本格式校验。
