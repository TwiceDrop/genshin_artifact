# 使用统计

Status: done

2026-11-12 与开发者逐条对齐。动手前先读根目录 `AGENTS.md`，它的规则优先于本规格。任务已拆到 `issues/`，按依赖顺序做：01 → 02 → 03，04 依赖 01 和 02，05～07 依赖 04。

## 给执行者

- 一个任务一次本地提交，不推送、不建 PR、不部署服务器。
- 使用统计不能改变任何计算结果，也不能阻塞或拖慢界面。
- 首次提示和设置项的文案要先交开发者定稿，下文的文案只是初稿。
- 每轮验证不超过五项。汇报时写清实际跑了什么，没在浏览器或真机上点过就不说实测通过。

## Problem Statement

开发者不知道玩家实际用了哪些功能。配装、四人轴、米游社导入、各种导出都在维护，但哪些功能很多人用、哪些几乎没人碰，现在没有任何数据，排优先级和决定是否删减功能只能凭感觉。

## Solution

客户端记下玩家每天用过哪些功能，匿名发到在线服务；开发者打开服务端的统计页面，看到每个功能有多少人用过。

- 一个"人"是一次安装：客户端第一次需要时在本地随机生成一个**匿名安装 ID**，不关联 UID、在线账号或设备信息。重装或清空存储会被算成新的人，这一点可以接受。
- 上报内容只有：**功能 ID**、匿名安装 ID、平台、软件版本、日期（精确到天）。不带 UID、角色、圣遗物、计算参数，服务端也不保存 IP。
- 默认开启。首次启动这个版本时提示一次，新安装和升级上来的玩家都会看到；设置页里随时可以关。
- 统计页面只给开发者看，放在在线服务上，用管理员 token 保护，不进玩家的安装包。

## User Stories

1. 作为开发者，我想看到每个功能累计有多少人用过，以便判断哪些功能值得继续投入。
2. 作为开发者，我想看到每个功能近 7 天和近 30 天的使用人数，以便看出功能的热度变化。
3. 作为开发者，我想看到每个功能占近 30 天活跃安装的比例，以便在不同时期之间比较。
4. 作为开发者，我想看到每日活跃安装数的折线，以便知道整体有多少人在用。
5. 作为开发者，我想按平台（Windows、Android）筛选统计，以便分别了解桌面 UI 和移动 UI 的使用情况。
6. 作为开发者，我想按软件版本筛选统计，以便看出新版本功能的接受程度。
7. 作为开发者，我想用一个 token 打开统计页面，以便不必维护一套账号体系。
8. 作为开发者，我希望没有 token 的人打不开统计页面，也查不到统计接口的数据。
9. 作为开发者，我希望统计页面上显示功能的中文名称，而不是内部 ID。
10. 作为开发者，我希望功能清单只有一份，客户端、服务端和统计页面都用它，以便新增功能时只改一处。
11. 作为开发者，我希望新增一个页面路由却没有登记功能 ID 时，测试会失败，以便不漏统计。
12. 作为开发者，我希望开发版和测试不上报，以便统计数据不被自己刷乱。
13. 作为开发者，我希望上报失败的阶段和原因出现在 Debug 导出里，以便玩家反馈时能排查。
14. 作为开发者，我希望服务端只接受登记过的功能 ID 和合法格式的安装 ID，以便挡住大部分乱发的数据。
15. 作为开发者，我希望服务端按 IP 限流，并限制单次请求的条数，以便接口不被刷爆。
16. 作为开发者，我希望服务端到期自动删除 400 天前的明细，同时保留累计人数，以便数据量可控、历史数字不丢失。
17. 作为开发者，我希望使用统计和账号、Cookie 托管的代码分开，以便改动一方不牵连另一方。
18. 作为开发者，我希望先部署服务端并验证，再发布带上报地址的客户端版本，以便客户端上线时接口已经可用。
19. 作为玩家，我想在第一次启动时知道软件会做匿名统计，以便自己决定要不要关。
20. 作为玩家，我想在首次提示里直接选择"关闭统计"，以便不必再去找设置。
21. 作为玩家，我想在设置页随时开关使用统计，以便改变主意。
22. 作为玩家，我希望关掉统计后立即停止上报，本地排队的记录和匿名安装 ID 也一起删掉。
23. 作为玩家，我希望重新开启统计时生成一个新的匿名安装 ID，以便和之前的记录无法关联。
24. 作为玩家，我希望上报不带我的 UID、角色、圣遗物或任何计算数据。
25. 作为玩家，我希望上报失败时不弹出错误提示，也不影响我正在做的计算。
26. 作为玩家，我希望离线使用时记录先存在本地，联网后再补发。
27. 作为玩家，我希望本地排队的记录有上限，不会无限占用存储。
28. 作为移动 UI 的玩家，我希望我的使用情况和桌面玩家一样被统计，入口和动作都不遗漏。
29. 作为开发者，我希望同一个人同一天多次使用同一功能只算一次，以便"多少人用过"的数字准确。
30. 作为开发者，我希望知道哪些关键动作被实际执行过（跑完配装、导入成功等），而不只是页面被打开过。

## Implementation Decisions

### 功能清单

- 一个独立的功能登记模块，是功能 ID 的唯一来源。每项包含：功能 ID、类别（入口访问或关键动作）、中文名称；入口访问的项还要写对应的路由路径。客户端用它决定能上报什么，服务端用它校验，统计页面用它显示名称。
- 在线服务的部署包本来就要求和本机服务目录放在一起，登记模块也一起打进部署包，不复制第二份。
- 入口访问（按路由自动记录，桌面 UI 和移动 UI 共用同一套路由）：配装计算、圣遗物仓库、圣遗物组、四人轴、角色预设、账号、UID 数据、历史记录、Playground、导出工具帮助、设置、介绍页。
- 关键动作（在动作成功的地方调用一次记录）：

| 动作 | 记一次的时机 |
| --- | --- |
| 单人配装 | 跑完一次，伤害模式和面板模式都算 |
| 动态圣遗物评分 | 跑完一次 |
| 四人轴计算 | 跑完一次，评估和搜索都算 |
| 米游社/HoYoLAB 导入 | 导入成功 |
| 导入圣遗物文件 | 导入成功 |
| 导出数据 | 账号页、圣遗物页的导出 |
| 保存预设 | 保存成功 |
| 保存圣遗物组 | 保存成功 |
| 清空已选 | 点击 |
| 切换外观 | 选择后 |
| 切换语言 | 选择后 |
| 检查更新 | 手动检查 |
| 安装更新 | 开始安装 |
| Debug 导出 | 配装页和四人轴页的导出 |

- 单次伤害会随输入改动不停重算，不作为关键动作，看"配装计算"入口访问人数即可。
- 移动 UI 是构建时选定的，没有运行时的界面切换动作；平台字段已经能区分两种 UI。
- 重定向路由（如在线账号入口）不单独登记。

### 客户端的使用统计模块

- 对外两个操作：记录一个功能 ID、发送队列。存储、网络发送、时钟、开关状态和上报地址都由调用方注入，页面和计算模块不直接碰存储和网络。
- 只接受登记过的功能 ID；传入未登记的 ID 是编程错误，开发时直接报错，不静默忽略。
- 本地队列按"功能 ID + 日期"去重，同一天同一功能只入队一次。
- 启动时、每 10 分钟、退出时各批量发送一次。失败的记录留在队列里下次重试；队列只保留最近 30 天、最多 500 条，超出时丢最早的。
- 发送失败不弹提示、不阻塞界面。本地只保留最近一次发送失败的阶段、原因和时间，附在配装页和四人轴页现有 Debug 导出的环境信息里，不新做全局导出入口（2026-11-12 开发者确认）。
- 上报地址在构建时写成常量，和玩家填写的在线账号地址无关。常量为空时整个模块不启用，开发版和测试默认就是空的。
- 关闭统计：立即停止发送，清空队列，删除匿名安装 ID。重新开启时生成新的 ID。
- 路由访问由一个全局的路由钩子统一记录，页面里不再单独记录入口访问。
- 首次提示：版本内第一次启动时显示一次，按钮为"知道了"和"关闭统计"，在玩家做出选择之前不上报（2026-11-12 开发者确认）。开关放在设置页，和外观、语言放在一起。初稿文案（待开发者定稿）："为了解哪些功能有人在用，莫娜会匿名统计功能使用次数，不包含 UID、角色、圣遗物或计算数据。可随时在设置中关闭。"

### 发送通道

- 桌面端经本机服务转发，做法和现有的在线账号转发相同，不需要处理 CORS。
- Android 用原生请求，做法和现有的在线账号原生请求相同。
- 使用统计的转发是独立的一条路径，不复用在线账号的会话或凭据。

### 在线服务

- 在在线服务里新增一个独立模块，只负责接收和查询使用统计；不读写账号、会话、Cookie 托管和快照相关的表。
- 上报接口：一次请求带一个匿名安装 ID、平台、版本，和一组"功能 ID + 日期"。校验内容：功能 ID 必须已登记，安装 ID 必须是 UUID，平台必须是已知值（Windows、Android），日期最早到服务器当天之前 30 天、最晚到之后 2 天，单次条数有上限。只要有一条不合格，请求整体拒绝，并返回是哪一条、什么原因（2026-11-12 开发者确认；过去的上限同日从 2 天放宽到 30 天，以便离线补发）。
- 限流按连接来源 IP 计数，IP 只在内存里用，不写库、不写日志。沿用现有的可信代理配置。
- 存储：一张明细表，"匿名安装 ID + 功能 ID + 日期 + 平台 + 版本"唯一，重复上报直接忽略；一张累计表，每个"匿名安装 ID + 功能 ID + 平台 + 版本"一行，写明细时同步维护；按任意筛选去重计数，跨版本相加也不会把同一个安装算两次。后台任务每天删除 400 天前的明细，累计表不受影响。
- 新增一个迁移文件，接在现有迁移之后。
- 查询接口：按平台、版本筛选，返回每个功能的累计人数、近 7 天人数、近 30 天人数、占近 30 天活跃安装的比例，以及每日活跃安装数序列。需要管理员 token。
- 管理员 token 作为 Compose secret 提供，和现有的其他 secret 一样由初始化脚本在缺失时生成，不打印内容。
- 统计页面：由在线服务直接提供的静态页面，打开时输入一次 token，token 只存在当前标签页的 sessionStorage 里。图表库从本地引入，不走外部 CDN。页面不接入主前端的 Vue 构建。
- 部署说明补充：新 secret 的位置和统计页面的地址。

### 术语

- `GLOSSARY.md` 新增：使用统计、匿名安装 ID、功能 ID。代码、文档和界面统一用这三个说法，不混用"埋点""遥测"。

## Testing Decisions

- 只测对外可见的行为：接口的请求和响应、模块对外两个操作的效果、登记清单和路由的对应关系；不测内部数据结构。
- 关键数字要有独立预期值：用合成的安装 ID 和日期构造数据，手算累计、近 7 天、近 30 天和占比，再和接口返回值比较。
- 测试接缝三处：
  1. **在线服务的 HTTP 接口**：用现有的 PGlite 夹具，和 `online-service` 现有测试的写法一致。覆盖：校验拒绝的各类输入、按天去重、限流、没有 token 和 token 错误时拒绝、统计数字、明细过期删除后累计数不变。
  2. **客户端的使用统计模块**：注入内存存储、假网络和假时钟。覆盖：同一天去重、跨天重新入队、发送失败保留并在下次重试、队列 30 天和 500 条的上限、关闭后清空队列和 ID、重新开启生成新 ID、上报地址为空时不启用、首次提示做出选择前不发送、失败原因能在 Debug 导出里看到。
  3. **功能清单一致性**：检查路由表里每条非重定向路由都有对应的功能 ID，功能 ID 不重复，客户端和服务端引用的是同一个登记模块。写法参照 `tests/kernel-entry-composition.test.mjs` 检查包装链的方式。
- 页面里关键动作的记录调用每处只有一行，不单独写测试；实现时逐项手动核对触发时机。
- 不跑全量测试。每个任务只跑和改动相关的测试文件。

## Out of Scope

- 漏斗、留存、单个用户的行为明细。
- 计算参数、角色、圣遗物、UID 等任何游戏数据的统计。
- 服务端"删除我的数据"功能：数据匿名，对不上具体的人。
- 防伪造的签名或客户端认证：接受少量噪音。
- 统计页面的账号体系和多管理员权限。
- 服务器的实际部署、域名和证书配置，以及带上报地址的客户端发版：这些在开发者明确授权后另行执行。
- 修改 README 或玩家可见的发布说明。
