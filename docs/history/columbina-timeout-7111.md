## 4. 每次评分为何昂贵

已核对保留内核中的f596结构，而非只依据旧Rust角色覆盖推断：它固定调用技能索引8、13、9、10、11、12六次，并应用12、4、5等轮转权重和充能需求系数。对应生成目录的ColumbinaDefault描述为两项技能伤害、12次持续伤害，以及按三种月伤比例合成的引力干涉。

每段通过f382进入完整伤害构造f72，并读取多类属性；同一目标还被用于大量分组／候选上界估值。`ValueFunction::get_attribute`会为评估组合创建属性图，`is_better_than_current_least`随后检查约束并计算完整目标。因而分组数量与完整目标成本相乘，在这组真实候选下放大了开销。

原目标函数即便某个应用比例为0，也是在6段伤害都结算以后才乘比例。当前原输入三项均为1，单纯跳过0比例分支不能解决这一份Debug。后续实现应考虑在每个候选内共享公共属性、只结算所需结果，并核对上界计算能否使用安全且更便宜的形式；不能冻结当前穿戴面板或简化为错误的纯生命／精通代理目标。

## 5. 已确认的共享排序缺陷

`cutoff_algo2.rs`中主词条、套装及单件排序使用类似 `-(score * 100.0) as usize` 的键。正收益分数取负后转无符号整数，会饱和成0，导致本应区别的优先级变成相同键。

该问题在实际原始WAT的f107中也成立：负100乘分数后，转换逻辑检查是否大于等于0；负值直接选择整数0，再写入排序键。不是仅凭当前Rust源码猜测旧二进制。

隔离对照只改f107的4处单件评分键：先得到非负评分，再取整数补码形成降序优先级。没有更改公式、候选、条件、精度或返回条数；控制值保持一致，但原全候选45秒仍未完成。因此目前只能确认缺陷与改进方向，尚未证明其足以解决超时。

建议生产修复使用明确的降序比较或Reverse，而不是把负浮点分数强转无符号整数。然后继续处理二加二阶段的分支数量、重复组合和每次完整评分成本。Any先搜四件套、再允许同套装与自身形成二加二，会重复检查部分四件套分组；去重需要保持所有合法方案与前100名结果语义，不作近似裁剪。
