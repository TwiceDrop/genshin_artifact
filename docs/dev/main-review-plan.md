# 莫娜占卜铺 main 分支审查计划

给 Claude Code 和复核结果的开发者。先回答三件事：这份代码能否对外发布，玩家的存档与隐私是否受保护，配装和伤害结果能否相信。最后用一条真实使用流程把界面、数据和计算串起来。

## 开工与交接

把下面这段连同文档链接交给 Claude Code；另开会话时，把批次号换成下一批并附上上一批摘要。

> 请执行《莫娜占卜铺 main 分支审查计划》第 1 批。先记录本轮 main 的完整提交号，后续各批沿用。只做审查，用合成数据，发现问题先给证据和影响，修复另行安排。每批只读本批入口、直接调用方和匹配的测试，按文末格式交接。

- **审查基线**：本计划按 `a45809f264cf82ff2fed25f043e80bdb658e72c3` 编写，显示版本为 `7.2.06.04`。开工时执行 `git fetch origin main`、`git rev-parse FETCH_HEAD`。若主线已前进，用新 SHA 审查并据此核对入口。文档所在分支只用于交付计划。
- **工作目录**：在干净的检出目录运行测试。已有工作树含个人改动时，可用 `git worktree add --detach ../mona-main-review <本轮SHA>` 单独检出。只读定位可直接用 `git show <本轮SHA>:<路径>`。先读该提交的 `AGENTS.md` 和 `docs/dev/current-state.md`。近期提交用于决定先看哪里，六批的范围覆盖整个固定快照。
- **额度分配**：每批先查一条常用路径和一个会改变结论的对照，通常一至两项验证就能收口。项目约定每轮最多五项，合跑多个批次也共用这五项。下列测试都是按需备选，命令为 `node --test tests/<文件名>`。已有证据足够就交接；只有普通操作可触发、后果严重或证据相互矛盾时，再沿直接调用链多查一层。

## 第 1 批 · 发行包与覆盖升级

**要回答的问题**：玩家会下载哪个包，升级后能否打开原来的存档，包里是否混入开发机文件？

1. 从 `docs/dev/release-checklist.md`、`package.json`、该版本发布说明确定目标形态。顺着 `script/build-web-package.ps1`、`tauri-exe/prepare-payload.py`、`script/build-android.ps1` 查实际复制清单，尤其是递归复制和构建机本地配置。分别记录托盘网页包、Tauri EXE、APK 的来源和版本；安装器若在交付清单内，再追到 `installer/mona.iss`。
2. 抽一条上一版到本版的正常更新，核对更新器选中的资源与当前形态一致。对照上一版的本机地址、端口、应用 ID 或签名指纹，看升级后是否仍打开原数据。出现文档与脚本端口不一致时，查实际启动参数；核对签名只看公开证书指纹。
3. 有同一提交的成品就抽查一个包内清单，核对实际包含的网页、内核、本地服务和额外文件。没有可追溯成品就交付源码层结论，并列出发版人需补看的一个包或清单。首轮无需为三端重建。更新资源选择可选 `release-update.test.mjs`。

## 第 2 批 · 未解禁内容与尚未开放的功能

**要回答的问题**：公开源码、玩家安装包、内容补丁和正常界面分别暴露了什么？哪些内容有公开依据？

1. 以最近一次已确认可公开的版本为参照，优先看变动的角色／装备注册表、生成的名称与翻译、`public/release-assets/`、轴样例及公开文档。结合第 1 批复制清单，标出内容经哪条路径进入源码、包或补丁。隐藏选择器只能说明 UI 的状态，文件随包分发仍需单独判断。
2. 对有疑问的游戏内容，只采信开发者确认的范围，或官方授权创作体验服视频已正式解禁并公开、且确实涵盖该项的依据。版本号、`beta` 文件名、社区爆料都不能确定公开资格。证据不足就列「待开发者确认」，记录路径和分发渠道即可，共享版报告省略敏感原文、图片和数值。
3. 对产品功能，抽一个入口从菜单、路由、平台开关追到实际处理。例如本基线的 `docs/dev/current-state.md` 写着米游社扫码暂时关闭，而 `tests/enka-showcase.test.mjs` 含打开扫码入口的用例。核对两者各自适用的版本和运行环境。只有确定发行配置、预期状态和实际可达性后才定性。内容补丁另抽一条，从 `server/patch-updater.mjs` 到签名验证和加载入口，确认其能带入哪些内容；签名证明来源，解禁依据仍按上一条核对。

## 第 3 批 · 隐私、导入与存档

**要回答的问题**：数据去了哪里？导入、切换 UID 或撤销时，会不会损坏别的账号或已有装备？

1. 复用第 1 批清单核对凭据、真实 UID／库存、Debug 导出、浏览器存储和签名私钥有无进入 Git 或成品。从 `server/credentials.mjs` 抽查一个读取凭据的调用方，只追到凭据实际发送或保存的位置。沿 `src/usage-stats/recorder.mjs` 查看首次选择前和关闭后的发送行为，结合 `src/components/CalcErrorDialog.vue` 区分用户主动导出和程序自动传输。共享报告只写字段名、去向和是否符合约定。
2. 建两个合成 UID。给 A 留一套已锁定或被预设引用的装备，给 B 留一件可辨识的装备。A 导入一次、重复导入、撤销，再切 B。核对件数、归属、装备 ID 和预设引用，B 的记录应保持原样。入口选 `src/import/uid-package.mjs` 和 `src/import/uid-import-session.js`；涉及 GOOD 或 Enka 时，仅加查实际走到的解析器。
3. 按疑点选 `uid-package.test.mjs` 或 `usage-stats-recorder.test.mjs`。本批交付一条数据流和一个前后对照；若发现凭据泄露或串档，记录影响路径后立即提示开发者。

## 第 4 批 · 单次伤害、配装与公共内核

**要回答的问题**：同一份角色、装备和条件，是否按约定的乘区计算，换一套候选装备后结果是否仍然成立？

1. 读 `docs/dev/formula-scope.md`。从 `mona_wasm/pkg/index.js` 和 `beta-tools/runtime.mjs` 找到共用的 `beta-data/compose-kernel-api.mjs`，看参数经何处传给原始发布内核、效果桥接内核或扩展内核。原始 WASM 以提交中的二进制为准；有变动迹象时才对比已确认基线的 Git blob。
2. 用同一个微型算例分别给出手算值与公共入口结果。普通直伤可设技能基础 100、独立倍率 1.5、定额 20，其他乘区取 1，无暴击，预期为 **170**。月曜直伤另选一个已有合成样例，只改最终擢升，核对本体与定额一起放大。可参考 `lunar-integration.test.mjs`，独立预期应来自公式或规格。
3. 选一种随装备变化的效果，用两个候选分别做单次计算，再核对配装排序。按 `docs/dev/add-character.md` 追踪面板、单次、配装、词条收益、DSL 五个公共入口中适用的字段与目标；只实算与样例相关的路径。怀疑两套入口发生分叉时，再选 `kernel-entry-composition.test.mjs`。

## 第 5 批 · 四人轴与搜索结果

**要回答的问题**：时间轴上是谁在什么时候打出这一击，换装后角色贡献、总伤与 DPS 能否对上？

1. 只取 `examples/team-dps/zibai-lunar-crystallize.json` 一条已维护的轴。从 `beta-data/team-engine/character-packages.mjs` 跟到相应角色包和公共反应模块，挑一次切人前后的命中，核对伤害所有者、命中时间和当时生效的 BUFF。用轴时长和明细独立验算一项贡献及 DPS；明确记录已知的近似时序。
2. 给一个来源角色换两套属性不同的装备，确认候选重算后排名与逐套直接求值吻合。若具体分歧指向 Worker 或 WebGPU，再用同一输入对照相关后端。CPU／GPU 数值相等只覆盖实现一致性，倍率和命中时序仍用上一步的独立预期判断。优先看 `team-zibai-rotation.test.mjs`，这条轴能回答问题即收口。

## 第 6 批 · 玩家界面与任务恢复

**要回答的问题**：玩家能否把已导入的角色用于计算，中途离开页面或取消后，结果还属于眼前这个角色吗？

1. 复用第 3 批的合成角色，走「UID 数据 → 选角色预设 → 单次伤害 → 配装 → 应用结果」。关注所选 UID、角色和装备是否一路一致，应用结果是否只改变玩家选择的内容。主要入口为 `src/pages/UidDataPage.vue`、`src/pages/NewArtifactPlanPage/`、`src/workers/`。
2. 抽一个常见中断：计算中切页后返回，或取消后换角色再算。检查进度、取消状态、迟到的 Worker 消息和最终结果。桌面宽度走完整条流程，再用一个手机窄屏宽度看关键按钮、弹窗与结果能否操作。可用浏览器时实走；仅有源码或 Node 环境时，可选 `progress-cancel.test.mjs` 或 `character-preset-workflow.test.mjs`，并标出尚待实测的那一步。

## 每批怎样交付

- **批次摘要**：写明 SHA、已走的玩家／发行路径、验证方式和结果。清楚区分源码核对、Node 测试、浏览器操作、成品检查。没有发现问题时写「本次样本未发现问题」，附具体样本。
- **每个发现一条**：写「优先级｜平台与入口｜普通触发步骤或可达路径｜预期与实际｜玩家影响｜文件:行号／测试名」。同一原因影响多个入口时合并报告。缺解禁依据、成品或设备时单列「待确认」，写清哪一份最小证据能定论。
- **优先级按后果排序**：已确认的未解禁内容进入拟公开源码、发行包或补丁，真实凭据泄露，可重复的跨账号数据损坏，均先报为发布阻断。常用配置稳定算错、更新错包、核心操作走不通列为高优先级。有可行绕行的一般问题简记。纯风格偏好、极端输入组合和无证据的性能猜测到此停止。
- **最后汇总一页**：先列发布阻断和最高优先级问题，再列需要开发者给出依据或实机复核的事项。每项只给能改变决策的下一步；审查结果由开发者决定是否进入修复和发布流程。
